## Question

A `<Suspense>` in an ERB view is meant to let the page appear before its slow
part is ready. In 0.0.19 it does not: the whole template runs before the first
byte. What does it take for the browser to get the shell and the fallback
first, and the content when it is ready — on a first load and on a navigation —
and what does that change for an app?

## What ruact does today

Measured against 0.0.19, with `ActionController::Live` in the controller
(today's best case), and slow work that waits at a gate the test opens:

- **Nothing reaches the browser while the gate is closed**: no headers and no
  body, for the document and for a Flight navigation. The template is one
  `render_to_string`; the content between `<Suspense>` and `</Suspense>` is
  evaluated there with everything else.
- On a navigation the browser keeps the old page, with no fallback. On a first
  load the tab stays on the previous document.
- After the work is done, a Flight navigation waits **another 1.5 s**: a
  `<Suspense>` with no `delay=` gets a default delay of 1.5 s, and the renderer
  sleeps before emitting the row it already has.
- The document never streams: its payload is one inline `<script>`.
- `load_async` alone changes none of this. With the async executor on, two
  queries started in the controller do run at once, and still nothing is sent
  until both are done, because the template that consumes them runs before the
  first byte.

## What was run

A Rails app in one file, with the middleware stack of an app generated by
`rails new` (checked class by class, in development and in production), behind
Puma with 3 threads. A prototype patches the gem at load time. It can deliver a
response in two ways, so the two could be compared on the same pages:

- **Live** — the action keeps running in the thread `ActionController::Live`
  gives it, and writes to the response as it goes.
- **Lazy body** — the action returns a Rack body; the server runs its `each`,
  and the blocks, after the action and the middleware have returned.

Slow work is `Gate.wait("a")`: it returns when the test opens gate `a` with a
request of its own. No scenario waits by time, with two exceptions that are
about time itself: the timeout, and one query that really takes seconds. The
test reads from the server that a block is waiting at the gate, looks at the
page, and opens the gate.
Where a result is the absence of something (nothing arrived, a block did not
start), it is read for a bounded time, and the results file says so.

1. **Browser.** Chromium, in development (Vite dev server) and against a
   production build: 10 scenarios per mechanism (9 in production, where the
   error overlay does not exist), plus the two that describe 0.0.19.
2. **The proof must fail without the prototype.** The same two proof scenarios
   run against 0.0.19; the runner checks that both fail, each at the assertion
   about what the browser shows.
3. **HTTP.** Buffering, a client that goes away, a timeout, `load_async`, what
   `Live` costs, what is written after the first write, what a middleware
   scoped around the request.
4. **Both client builds.** The browser scenarios again with React 19.2.8 and
   the app's own `react-server-dom-webpack`.
5. **The new document with the old JavaScript.**

## The result

With the gate closed, the browser shows the shell and the fallback; an island
in the shell takes clicks; opening the gate replaces the fallback with the
content, in the same document, and the island keeps its state. This holds on a
first load and on a navigation, with both mechanisms, in development and in
production, with both client builds (*measured*: `results/browser.md`).

The prototype changes four things in the gem's pipeline, and the serializer is
not one of them:

1. The preprocessor turns the content of `<Suspense>` into the block of a
   helper call. Evaluating the template no longer evaluates it.
2. The helper registers the block, with the view it closes over, and leaves a
   marker.
3. The converter turns the marker into a Suspense whose child is a reference to
   that block.
4. After the shell is written, an orchestrator evaluates one block, converts
   its HTML, serializes its row and writes it; then the next.

The rows are the ones 0.0.19 already writes (`"$Sreact.suspense"`, a `$L`
child, the `ruact:boundary` wrapper, an `E` row with a digest). Only when they
are written changes.

## Decisions

### D1 — What the developer writes

**Options.** (a) The content of `<Suspense>` is what runs later; the view is
written as it is today. (b) The app marks a value as deferred
(`@report = defer { … }`) and `<Suspense>` waits for it. (c) Both.

**Evidence** (*measured*, with (a)):

- A slow call inside the tag is deferred as written.
- A lazy relation is loaded where the view walks it, so
  `@comments = Comment.where(…)` in the controller is deferred: one connection
  is busy while it runs and is back in the pool afterwards.
- Components, partials, a nested `<Suspense>` and `t(".lazy")` work inside the
  block, and what the block prints is escaped as in any template. `t(".lazy")`
  needs the template path restored first; without that it raises.
- **`load_async`, with the executor configured**: two queries started in the
  controller run at once (two connections busy), the shell is at the client
  before either finishes, and each block waits only for what is left of its
  query. The queries here wait in Ruby, at a gate; a query that computes
  inside SQLite holds Ruby's lock while it runs (see the timeout, D2), so how
  far real queries overlap is a question for PostgreSQL, not answered here.
- **`load_async`, without it** (the default of a generated app:
  `config.active_record.async_query_executor` is `nil`): the call loads the
  relation right there, in the controller. The first query blocks the
  action and nothing is sent. This is worse than not calling it, since a plain
  relation would have been loaded inside the block.

**Choice: (a).** It is what the tag says, and it needs nothing new from the
view. `load_async` is the recommended way to start queries early, and it is an
application setting, not something ruact turns on.

- The rule that follows: **work the controller does before rendering is not
  deferred.** `@report = Report.compute` runs before the view exists.
- In development, a `load_async` that cannot be asynchronous says so in the
  log, naming the setting (Luiz, 2026-10-13). `ruact:doctor` reports the
  setting too. The warning belongs on the `load_async` call rather than on
  every `<Suspense>`: an app that never calls it has nothing to fix.
- By Rails' source, and not measured here, `load_async` is also synchronous
  inside a transaction, and runs on the caller when its pool's queue is full.
  The guide should say both.
- A `<Suspense>` with nothing slow costs one extra row, written right after
  the shell.

**Rejected: (b), for now.** Nothing measured needed it. For queries,
`load_async` already is the explicit "start now, read later". For other work
(an HTTP call) a future from concurrent-ruby, started in the controller and
read inside the tag, would play the same part; that was not measured and is
not part of the next story.

### D2 — How the blocks are evaluated

**Choice: one block at a time, in the order the page has them, on the thread
that runs the action. ruact starts no thread and no fiber.**

**Evidence** (*measured*). This is enough for the proof. With two boundaries
and the second gate opened first, nothing changes until the first opens; then
both arrive. With `load_async` the two queries run at once anyway: what is
ordered is only when their rows are written.

**Why not more.** A thread per boundary needs a database connection per
boundary and a copy of the request's state per thread, and the parallelism it
buys is already there for queries through Rails' own pool. Fibers need a
scheduler Rails and Puma do not run.

**A response that is open holds a server thread**, as any slow action does.
With Puma's 3 threads, three responses waiting at their gates left none to
answer another request (seen while writing the measurements; no script keeps
it). Streaming changes when the browser gets the page, not how many slow
requests a server can hold.

**The known limit.** A block that is ready waits behind an earlier one that is
not. The total time is the same; what is lost is seeing the faster part first.
Writing rows as their work finishes is possible later for blocks backed by
`load_async`, and nothing here prevents it.

**Timeout.** Each block runs under `suspense_timeout`. For work that waits in
Ruby — the gate, here inside a SQL function — the boundary gets the error row
with the digest `ruact:suspense-timeout` once the limit passes, the next block
runs, and a page that queries the same pool afterwards reads its rows
(*measured*).

**It does not bound a query that runs inside SQLite** (*measured*): with a
1 s limit, a query that took about 4 s ran to its end and the boundary got
its content. Ruby's `Timeout` interrupts a thread only where Ruby can run,
and the SQLite driver keeps Ruby's lock for the whole query. A driver that
waits on the network without that lock, as PostgreSQL's does, is expected to
be interruptible there; that was not measured.

What the next story has to carry:

- The timeout must not be an exception the block can rescue. Raised as an
  ordinary one, it came back from a query wrapped in
  `ActiveRecord::StatementInvalid` and was not recognised (seen with the first
  version of the prototype; no script keeps that version), and a `rescue` in a
  view would have swallowed it.
  `Timeout.timeout` with no exception class unwinds the block with one that is
  not a `StandardError`.
- It is a limit by interruption, on the one thread there is: it lands
  wherever the block happens to be, as `rack-timeout` does; an `ensure` that
  blocks delays it; and native code that does not yield is not interrupted at
  all. **`suspense_timeout` is a backstop, not a guarantee.** The limit that
  holds for a query is the database's own statement timeout, and the guide
  has to say so.

Today `suspense_timeout` compares against the declared `delay`. It becomes a
limit on real time, as far as the block can be interrupted.

### D3 — What the block still has of the request

The block runs in the view it was written in: same instance variables, locals
and helpers. What it sees beyond that depends on the mechanism (*measured*,
with the block waiting at a gate so that the order is certain;
`results/context-*.json`, `results/http.md`):

| What the request set up | Live | Lazy body |
| --- | --- | --- |
| `around_action`: `I18n.with_locale`, `Time.use_zone`, a tenant | **kept** | **gone** (default locale, UTC, no tenant) |
| `CurrentAttributes` | kept | kept |
| `t(".lazy")`, once the template path is restored | resolves in the request's locale | resolves in the default locale |
| `after_action` | runs after the last block | runs before the first |
| A middleware that scopes the request around the app (`connected_to(…, prevent_writes: true)`) | **gone** once the response has started | **gone** |
| A locale a middleware set | the action sees its pool thread's locale, which may be another request's (below) | the shell sees it, the block does not |
| A thread variable a middleware set | not visible, in the shell either | visible |

**Choice: the block runs while the action is still running** — Live's model.
What the controller scoped is then still in force, and that is where an app
puts its tenant, its locale and its time zone.

**What neither mechanism can keep** is what a middleware scopes around the
app. A response starts by the middleware returning; the blocks run after that.
That is how a streamed response works in Rack, not something of ruact's. For a
page that streams, a scope the
deferred content depends on has to be set in the controller. This needs a line
in the guide, and it is a case for 19-2 with Rails' `DatabaseSelector`.

**Two things about `ActionController::Live` itself**, the same in 0.0.19 for
any controller that includes it, deferred content or not (*measured*, with
i18n 1.15):

- The action runs on a thread from a pool, and sees the locale that thread
  has. A thread created for a request inside a middleware's
  `I18n.with_locale(:pt)` saw `pt`, and still had `pt` for the next request, to
  a page with no such middleware. A thread that already existed kept its own
  locale, and the middleware's did not reach the action. A locale set in the
  controller is not affected: it is set and restored on the action's thread.
- Thread variables set outside the action are not visible in it. Live copies
  fiber-locals and shares Rails' execution state, and thread variables are
  neither.

### D4 — Releasing what a block holds

On Rails 7.2 and later a query on a model takes a connection for the query,
so a block holds one only while a query is running. Three facts shape the
design (*measured*):

- **A connection leased for the request is not returned under Live.**
  `Model.connection` leases one to the thread until the request ends. Rails
  returns it from the request's thread, and under Live the action ran on
  another: after one request to a page that calls it, one connection stayed
  busy; after two more at once, two. With the lazy body none did. This is
  Rails' behaviour and the same in 0.0.19, on a page with no `<Suspense>`
  either; the connection stays with Live's pool thread.

- **The server does not learn that the client left while a block is waiting.**
  The block keeps its connection until it ends or times out. With the client
  gone and the gate never opened, the timeout ended the block and the
  connection was back in the pool.
- **The first write to a client that left does not fail.** After the client
  disconnected, the row of the first block was written without error and the
  second block started, in both mechanisms. Asking the socket before each
  block (`puma.socket`, a non-blocking peek that reads end-of-file) stops
  that: the second block did not start.

**Options.** (a) Do nothing: a block for a client that left runs to its end.
(b) Ask before each block, and bound a running one with the timeout. (c) Watch
the socket from another thread and interrupt the block.

**Choice: (b).** Before each block, ask whether the client is still there,
where the server offers a way; never start a block for a client that is gone.
When the action ends, the gem returns what the action's thread leased, as
Rails does for the request's thread.
A block already running ends by itself or at `suspense_timeout`, with the
limits D2 gives for that. Nothing is cancelled from outside.

**Rejected.** (a) leaves every later block of an abandoned page running. (c)
is a thread per streaming response to save, at most, one `suspense_timeout`.

React, Next.js and Waku do not stop the application's work in flight either:
they abort the render, stop writing and drop a result that arrives late, and
work is cancelled only if its own code asked for React's `cacheSignal()` (read
in their sources: React's `ReactFlightServer.js` at `b91823e`, Next.js at
`f3f56ece`, Waku at `8e9f542`). There a pending
promise holds nothing, and here the block holds a thread and maybe a
connection, which is why the timeout is part of the design and not an option.

A client that half-closes its connection and keeps reading would read as gone.
Browsers and proxies do not do that to a page; it is noted, not handled.

### D5 — How the response is sent

**Options for the first load.** (a) Stream the document: send it up to
`</body>`, then each later batch of rows as a script, then the end. (b) Send
the document complete, with the shell only, and have the browser fetch the
rest. (c) Leave the first load as it is and stream only navigations.

**Choice: (a).** The layout renders with the shell's rows inline, as today.
The document is sent up to `</body>`; each later batch of rows is a
`<script>self.__FLIGHT_DATA.push("…")</script>`; then `</body></html>`. A
navigation gets the same rows over `text/x-component`, as the Live path writes
them today.

**Rejected.** (b) runs the action twice, or needs a place to keep a
half-rendered page between two requests. (c) is the scope question below.

**The response starts at the first write.** What is written to it later races
with the headers being sent, and has lost once anything waited (*measured* for
a header, a cookie and the session; the status and the flash travel the same
way):

| Written after the first write | Live | Lazy body |
| --- | --- | --- |
| A cookie and a session value, by a block that waited at a gate | lost | lost |
| A cookie, by a block that did nothing that lets another thread run (600 responses) | 600 arrived | 0 arrived |
| A header and a cookie, by an `after_action` that waited at a gate | lost | arrive (the filter runs before the response starts) |

So, inside a `<Suspense>`:

- An exception is not a 500. The response is already 200; the boundary gets an
  error row, keeps its fallback, and the blocks after it still run. The
  exception goes to `Rails.error` (*measured*) and to the log.
- A record that is not found is not a 404, for the same reason.
- There is no redirect. Next.js emits a client-side one for this case; ruact
  does not copy that.
- A cookie, the session and the flash are not to be written. Under Live such
  a write can work in a quick test and vanish once the block does real work,
  which is the worst way for it to fail: it should be an error in development.

What decides status and redirects is the controller, before rendering, as in
any Rails action. Rails' own streaming has the same rule, and so does Next.js.

**An exception that escapes while the response is open.** By its source, Live
then appends a script that sends the browser to `/500.html` to an HTML
response that is still open. The prototype rescues every block's error and
closes the stream in an `ensure`, so nothing escaped with the stream open; the
implementation has to guarantee that, and it is a case for 19-2.

**Errors in development** (Luiz, 2026-10-13). The browser can put the error
over the page: the experiment draws an overlay with the exception's class and
message and the Ruby backtrace, which React's development client rebuilds from
the row (`results/overlay-live.png`). In production the row carries a digest
and a fixed message, nothing of the exception, and the page says only that
the part failed.

**What the browser runtime has to change** (*measured*: with 0.0.19's
bootstrap the fallback never shows; the third was found as a failure):

1. The entry script has to run before the document ends. A module script is
   deferred, so it would run after the last row; it becomes `async`. In
   development the react-refresh preamble has to run first, so one async
   module installs it and then imports the entry.
2. The bootstrap reads `__FLIGHT_DATA` as a stream: it takes what is there,
   replaces `push`, and closes when the document does.
3. The error handler has to be installed before the first render. The router
   installs it in an effect today; a row that is already an error when the
   page mounts is caught before that effect and never reaches it.

**The new document with the old JavaScript** (a tab or a cache that still has
0.0.19's bootstrap) shows the whole page when the document ends and never the
fallback (*measured*). Nothing breaks; the page is as late as it is today.

### D6 — `ActionController::Live`

Live is decided before the action runs: it runs the action in a thread of its
own and gives it a response whose body is a queue. "Does this page have a
`<Suspense>`?" is only known once the template has run, so it cannot be what
turns Live on. What can: the action's name, which the route has already
decided. The experiment did that — Live for some actions of a controller and
not for others — and the action left out ran on the request's thread with its
usual response (*measured*). It did so by overriding `process` and
`make_response!`, which a Rails upgrade can change under it; including Live in
a whole controller is the way Rails documents.

What Live does to an action that uses it, **on a page with no `<Suspense>`**
(*measured*):

| | With Live | Without |
| --- | --- | --- |
| `ETag` | none (`cache-control: no-cache`) | sent; a Flight request with `If-None-Match` gets a 304 (not checked for the document) |
| A locale set by a middleware | the pool thread's: this request's or an earlier one's (D3) | seen |
| Thread variables set by a middleware | not visible | visible |
| A connection leased with `Model.connection` | still busy after the request, one per pool thread (D4) | returned |
| An `after_action` that writes a header or a cookie | arrived in 600 of 600 when the filter did nothing that lets another thread run; lost when it waited at a gate | arrives |
| Requests per second, trivial page | a few percent fewer in `results/http.md`, where the two configurations without Live also differ from each other | — |

By Rails' source, not measured here:

- Rails' test support replaces Live's thread with an inline call, for the
  whole process, once it is loaded. Controller tests, request specs and system
  tests that run the server in the test's own process then run the action to
  its end before anything is sent: **they cannot see a fallback, nor the
  thread and the ordering the rows above come from.** Streaming can only be
  tested against a server started on its own, as this experiment does.
- In development a code reload waits for a streaming action to finish.

**Options.**

- **(A) The app says which controllers or actions stream**, with one line
  ruact provides (working name `ruact_streaming`, taking `only:` like
  `ruact_pages`), which applies Live to those actions. A `<Suspense>` rendered
  by an action that does not stream evaluates in place, as in 0.0.19, and says
  so in development, naming the controller and the line to add.
- **(B) ruact turns Live on for every page action.** The app writes nothing.
  Every ruact page takes the rows above, with or without a `<Suspense>`.
- **(C) No Live: the lazy body.** Decided at render time, nothing to declare,
  no cost for other pages. Rejected by D3: what the controller scoped is gone.
- **(D) ruact learns which actions stream** from their first render.
  Rejected: the first response of each action differs from the rest, per
  process, which is hard to explain and to test.

**Recommendation: (A).** A controller that does not include Live today keeps
the behaviour it has. The
failure it leaves — a `<Suspense>` in an action that does not stream — is
detected with certainty at render time, so it can be loud. (B) is the better
experience when it works, and what it costs is silent and lands on pages that
have nothing to stream: no `ETag`, and an app that picks its locale in a
middleware can get another request's. An app that wants (B) gets it with the same
line in `ApplicationController`.

(A)'s own path for a `<Suspense>` in an action that does not stream —
evaluated in place, with a development message — was not prototyped: it is
what 0.0.19 does, plus the message.

**Decided (Luiz, 2026-10-14): (A).**

## Buffering

*Measured*, with the generated app's middleware stack and Puma, in development
and in production: **the shell reached the client before the gate opened in
all 24 combinations** — both mechanisms, the document and a Flight response,
with the default stack, with `Rack::Deflater` added (the client decoding gzip
as it arrives), and with the prototype's own headers removed.

- `Rack::ETag` in Rack 3 digests a body only if it is an array. A streamed
  body is not, so it is left alone and gets `cache-control: no-cache`.
- `Rack::ConditionalGet`, `ActionDispatch::ServerTiming`, `WebConsole` and the
  reloader did not hold the response either.

The headers the gem sets on a streamed response stay as the Live path has them
today: `Cache-Control: no-cache` and `X-Accel-Buffering: no`.

## Not measured

- **Rails before 8.1.** The gem's test matrix runs Rails 7.0 to 8.0, and not
  the 8.1 everything here ran on. Before 7.2 a thread keeps its connection for
  the whole request, so D4's "only while a query runs" does not hold there.
  *Since 19-1:* the matrix named 7.0 and 7.1 but ran 7.2 in those cells; the
  supported range is now 7.2 through 8.1 (Luiz, 2026-10-14), each cell checks
  the Rails it loads, and 8.1 is in it. Before 7.2 is no longer a case.
- **i18n before 1.15**, which kept the locale in a thread variable: by D3's
  second bullet a Live action would then not see a locale set outside it at
  all. *Since 19-2 (`e2e/middleware.spec.mjs`, `./run i18n 1.14.7`):* with
  1.14.7 a block loses the locale a middleware set; with 1.15.2 the shell
  and the block showed `pt` in some runs and `en` in others (the committed
  `results/middleware-*.json` of different runs), the cause not established.
  The locale a middleware set is not to be relied on with either.
  Rails' `DatabaseSelector` (primary and replica, `/role`): the shell reads as
  `reading`, a block that runs later as `writing` — the selector's
  `connected_to` ended when the response started; with the role set in the
  controller (`around_action { connected_to(role: :reading) { … } }`) the
  block reads as `reading` too (`results/database-selector-*.json`). A
  `prevent_writes` a middleware set is gone for a block the same way. A tenant
  kept in Rails' execution state is copied to the action's thread. Scopes
  belong in the controller.
- **Rack 2.2**, whose `ETag` buffers any body unless it sees
  `Cache-Control: no-cache` or `Last-Modified`.
- **A reverse proxy.** By its documentation nginx buffers a proxied response by
  default (`proxy_buffering on`) and honours `X-Accel-Buffering: no`, which the
  gem sends; a proxy that compresses, or that ignores that header, has to be
  configured not to buffer. The guide has to say this with the header names.
- **Other servers**; Puma terminating TLS itself (the socket check reads a
  plain socket); HTTP/2.
- **PostgreSQL and MySQL**: whether the timeout interrupts a running query
  there, the connection after it did, and how far `load_async` queries
  overlap. *Since 19-1, PostgreSQL (14, pg 1.7):* the timeout returns control
  at the limit — the block ends, its boundary gets the timeout row — but the
  query keeps running on the server, and the next query on that connection
  waits for it (`SELECT pg_sleep(4)` under a 1 s limit: 1.00 s, then 3.03 s
  for `SELECT 1`). A `statement_timeout` cancels it at the limit
  (`ActiveRecord::QueryCanceled`, nothing left running).
  `spec/browser/deferred_suspense/results/postgres.md`, `./run postgres`.
  MySQL and overlapping `load_async` queries are still not measured.
  *Since 19-2 (`./run pg`, `e2e/postgres.spec.mjs`):* ruact cancels the
  query in flight at the limit (`QueryWatch`), so the next query on that
  connection no longer waits; a `statement_timeout` cancels it with
  `ActiveRecord::QueryCanceled`, an error of the block; two `load_async`
  queries were active at once with the executor while the shell was on
  screen, and without it the controller held the shell until both ran. By
  design, not measured: a query `load_async` runs is not cancelled at the
  limit (the executor's thread holds its connection), so the statement
  timeout is its limit. MySQL is still not measured.
- **The writes that race**, on a machine under real load.

## The wire and the two clients

No row changes shape. The browser scenarios pass with the client vendored in
the gem (19.3.0) and with the app's own `react-server-dom-webpack` 19.2.8, in
development and against a production build (*measured*). The three runtime
changes under D5 are in ruact's bootstrap and entry tag, not in React's client.

## What does not change, and what does

**Kept.**

- No Node in production.
- The serializer stays pure. It is handed elements and writes rows; evaluating
  a block, converting its HTML and deciding when to write are the
  orchestrator's.
- Rails' escaping and ruact's serialization rules apply inside a block: it is
  the same template code, captured by the same view (*measured* for escaping).
- An action that does not stream answers as it does today. For a page with no
  `<Suspense>` the prototype's Flight response, and the payload inlined in its
  document, are byte for byte what 0.0.19 sends (*measured*). The document's
  entry tag is what changes, for every ruact page (D5).

**Changes, for the changelog.**

- The content of `<Suspense>` runs after the shell is sent, in an action that
  streams. Code that relied on it running before a later part of the template
  (setting an instance variable the rest of the page reads, `content_for`) no
  longer can.
- A `<Suspense>` with no `delay=` waits for nothing. Today it waits 1.5 s on a
  streamed navigation. `delay=` stays as an explicit wait before the block
  runs, for seeing a fallback in development; it counts against
  `suspense_timeout`, so a delay longer than the timeout still ends in the
  timeout row, as today.
- `suspense_timeout` limits real time, where the block can be interrupted (D2).
- An error inside a `<Suspense>` no longer makes the response a 500.
- The first load streams too.
- If (A) is chosen: a controller that includes `ActionController::Live` keeps
  streaming, and `ruact_streaming` is the documented way. A controller with
  neither answers as it does today, and in development a `<Suspense>` it
  renders says what to add.

## Implementation (19-1)

What the gem does, where it differs from the prototype of 19-0:

- **The seam.** After the 19-0r refactor the prototype's four patches became
  one change each at its seam: the `<Suspense>` helper keeps its block in the
  render context when the action streams (`ViewHelper::Suspense`); the
  converter turns the marker into a Suspense whose child is a reference to the
  block (`Flight::DeferredContent`); `DeferredRender` evaluates the block when
  the renderer hands its boundary out (`Renderer#take_boundary`), outside
  `lib/ruact/flight/`; `Controller::Delivery` writes the shell, asks for the
  client before each block, and pushes each boundary's rows into the document
  or the Flight body.
- **D6 (A)** is `Controller::Streaming`: Live included by `ruact_streaming`,
  bypassed per action — `make_response!` (the response) and `process` (the
  thread) both decide by the action's name, which `Controller.action(:name)`
  passes along in the request. The prototype read the route, which an endpoint
  built with `.action` does not name.
- **HTTP/1.0.** Live answers it with an ordinary response, which the server
  sends whole as soon as anything is written; the gem defers only when the
  response is Live's, so over HTTP/1.0 (nginx's default to its upstream) the
  page renders in place, whole. Found in review R3: a deferred render there
  sent the shell alone.
- **Order.** A `<Suspense>` inside a block is queued behind the boundaries the
  page already had (the prototype did the same): blocks run one at a time,
  each queue in page order.
- **Writes after the response started** are compared, in development, before
  and after each block (headers, cookies, session, flash) and become the
  block's error; after the last block, an `after_action`'s are logged. Rails
  itself accepts them and drops them.
- **Connections.** At the end of a streamed action the gem releases what the
  action's thread leased (`clear_active_connections!(:all)`), when that thread
  is not the request's.
- **The proof** is `spec/browser/deferred_suspense/` against the gem, in CI;
  this ADR's experiment stays the record of 19-0, against `v0.0.19`.

What 19-2 changed, from the lifecycle cases:

- **Locals.** A block that runs later read a local as it was then — every
  block of a `for` loop showed its last item. The helper keeps the locals the
  block sees when the tag is met; `DeferredRender` gives them back while it
  runs. Instance variables are read when the block runs.
- **Markers carry the render's id.** A `cache` block stores markers of the
  render that wrote it; read back, they named another component or another
  boundary's block. Now a component read from the cache raises, and a
  `<Suspense>` read from the cache gets an error row for its boundary.
- **Leaving an open document.** The router stops a document it leaves — a
  link, a form; not `revalidate()`, which stays on the page — while it still
  streams (`window.stop()`; the server marks such a document), so its
  connection closes and the server starts no further block; the rows of the
  page being left end as an aborted navigation, not as a response cut short.
  Stopping it stops the rest of what the document was loading — measured in
  Chrome (`e2e/leaving.spec.mjs`, `results/leaving-*.json`): an image still
  loading stays broken, a `fetch` in flight fails with `TypeError`, a module
  `import()` in flight fails and importing it again works. A *fetch* the
  router aborts is different: Chrome sometimes keeps reading an aborted
  response to reuse its connection, and the server then renders its next
  block — seen in production on 2026-10-15
  (`results/navigation-*.history.jsonl`), not preventable from either side.
- **`no-store`** on a streamed Flight response: Chrome held a second request
  for the same URL (`revalidate()`) while the first, storable, streamed.
- **A query past the timeout is cancelled** (PostgreSQL, `QueryWatch`).
- **After the response started:** an `after_action` that raises is reported
  to `Rails.error`; `content_for` inside a block is an error in development.
- **Errors' positions:** the error row's frames are the six fields React's
  development client reads, and a component tag over several lines keeps
  them, so the template lines are right.

## Decided by Luiz

On 2026-10-14:

1. **D6: (A).** The app declares what streams, with `ruact_streaming`, and is
   told loudly in development when a `<Suspense>` renders in an action that
   does not.
2. **Scope of 19-1: together.** The first load and the navigation stream in
   the same story. The server side is the same code for both, and the
   navigation alone would leave the first load, the one every visitor gets,
   as it is.
3. **`suspense_timeout` stays at 5 s** once it limits real time. It is a
   backstop: it does not stop a query the driver cannot interrupt, and the
   guide says so.

On 2026-10-15 (Story 19-2a):

4. **A transaction left open at the end of an action is not rolled back by
   ruact.** The next request inherits it with and without streaming: that is
   Rails, and ruact does not undo for the app what Rails leaves alone
   everywhere else. The guide says so.
5. **The router keeps stopping a document still streaming when it leaves the
   page by a link or a form**, so the server renders nothing for a page nobody
   sees. The cost, measured, goes in the guide: what that document was still
   loading (an image, a `fetch`, an `import()`) fails.
6. **The browser job is a required check** for merging into the gem's `main`
   (five green runs in a row, without retry, after the last change of 19-2a).
